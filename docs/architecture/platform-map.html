Hawkes Platform Map

Two services run every Hawkes project. Studio manages the work: it hears pushes, runs AI agents, judges playtests and moves code toward live. Gen does the heavy compute: one job queue in front of GPU providers, build machines and playtest browsers. GitHub is the source of truth for code, and Cloudflare fronts everything.

Blueprint

Every running piece, grouped by where it lives. Each box has an id (A1, C5…) that the wiring list and build sheet below refer to. Numbered arrows are the main paths; the wiring list has all of them.

What this page carries: the shape, every resource by name, every connection, and the order to bring it up. What it cannot carry: the code (it is in the repos named in F1), secret values, and the data in the databases and buckets. With the repos and fresh credentials, this is enough to rebuild the platform empty; restoring it with its data also needs the bucket backups.

Bring-up order

From nothing to the running platform. Each step depends only on the ones before it.

  1. Accounts. A Google Cloud project for Studio and Gen and one for the portal and Net; a Cloudflare account with the zones; the GitHub account with the repos; RunPod and Modal; Stripe; a Google sign-in client.
  2. Identity for deploys. The Workload Identity pool, a provider per repo and the deployer service accounts, from each repo's CI setup script.
  3. Buckets and secrets. The state, library and backup buckets; the secrets in the secret manager.
  4. Gen. Push Gen's main: CI builds the image and creates the service. Set its owner key, then its settings: storage, Unity build backend, playtest backend.
  5. Gen's helpers. Deploy the CPU services, the software-playtest service and the Unity build job.
  6. Worker images. Push the image tags so the GPU, 3D and playtest images build.
  7. Rented compute. Create the RunPod endpoints and the Modal apps from those images; register them in Gen's provider list and order; run the playtest self-test.
  8. Gen's edge. Deploy the gen-edge and gen-cdn Workers with their routes and DNS records.
  9. Studio. Push Studio's main. Give it its keys, its Gen key, its GitHub token and the Google client; turn on cells for the control plane.
  10. Studio's edge and beta sites. Deploy studio-edge and beta-sites, create the R2 bucket, add a route per product host.
  11. Schedules. Create the nightly run, the cells' cron and the Gen backup.
  12. Harness logins. Sign in to Claude from Studio's settings; add any other harness.
  13. Portal and Net. Deploy the portal to Firebase; provision the two Net VMs and let them pull their branches.
  14. Projects. Create a studio (a cell), connect GitHub, and add each project: the hook workflow, the three branches, the playtest bot, its builds and scenarios, its Gen preset.
  15. Prove it. Push to a project's beta and watch the beta site republish; run one playtest; go live once.

Studio and Gen share one shape: a single Node process, no build step, one SQLite file, one writer at a time. A lease in the bucket hands the database from an old revision to a new one, so a deploy never has two writers.

How work flows

A change travels the same path whether it starts from you, a bug report or the backlog.

  1. Direction. You say what you want in Talk. Talk proposes a roadmap item with tasks and acceptance criteria and adds them on your yes.
  2. Start. Every 60 seconds the PM loop picks startable tasks and the worst open bugs, within its caps (2 at once, 3 tries per task).
  3. Agent pass. Studio packs the repo state into a bucket folder and starts a Cloud Run job. The agent works on a branch cut from beta with no Studio secrets.
  4. Pull request. Studio unpacks the commits, pushes the branch and opens the pull request into beta itself.
  5. Checks. The project's checks run. Unity changes pass a compile gate instead of a full build.
  6. Merge into beta. Product changes that pass merge by themselves. Changes to Studio or Gen need green CI and merge under walk-away mode or your tap.
  7. Beta site. The push to beta fires the hook, and Studio republishes the beta site to R2, sending only changed files.
  8. Milestone play. When every task in a milestone is merged, Studio has Gen build and playtest beta, then two judges score each criterion. "Unclear" never passes.
  9. Go live. On your word (or a project's auto policy) Studio fast-forwards main to the playtested beta commit. GitHub Pages publishes it and Studio checks the live site.

Studio

Platform Studio and cells

The Studio at studio.hawkesgen.ai is now the control plane. It holds no projects of its own, only Studio and Gen as infrastructure targets. Each customer studio is a separate Cloud Run service with its own database prefix, cookie, Gen key and project prefix. Yours is the cell j-studio-4f12, where every game moved on 2 Nov 2026. An edge Worker routes /o/<org>/ to the right cell and wakes hibernated ones.

The loops inside it

  • PM loop: a 60-second tick that syncs tasks, settles questions, prices GPU budgets and starts work.
  • Nightly run: triggered at 05:00 Pacific. It now checks git state, runs checks, the story map and asset status, then writes the morning brief. It no longer builds or playtests.
  • Milestone check: the only automatic trigger for a build and playtest, besides a go-live request.
  • Holds: a 60-second review of any AI harness that is out of usage, billing or sign-in.

What it stores

Everything is in one SQLite file: runs and steps, findings (the backlog and ideas are both rows here), roadmap items, tasks and milestones, changes (one row per agent pass or pull request), approvals, deploys, the pass ledger, and the shared memory with full-text search.

Guards

  • Agents reach Studio only through a restricted tool set, with a key that Studio treats as the sandbox user.
  • Going live needs your own words or a project's auto policy; a message that arrived through MCP never counts as your words.
  • Merging a change to Studio or Gen still needs the exact phrase MERGE <id> or walk-away mode.
  • GPU budgets under $5 are approved automatically; walk-away mode allows $25 a day.

Gen and its job queue

Rules of the queue

  • States: queued, running, done, failed, cancelled. A job with the same key returns the existing job; reuse returns a finished job with the same recipe.
  • Lanes: each non-GPU provider has its own concurrency (voice 3, Claude 4, local 2). GPU jobs wait for a provider with room.
  • Fair share: customer projects take turns, 2 GPU jobs and 2 per lane each, at most 20 waiting. Studio's own projects are exempt.
  • Batching: a free GPU takes the next job of the model family it already has loaded, so models are not swapped between every job.
  • Ceilings: new jobs are refused once the day's spend reaches $200.
  • Retries: there is no general retry. Specific failures requeue: provider unavailable, a planned restart, a crashed graph.

Tools

A tool is either code or a ComfyUI workflow folder. Importing a workflow drafts its inputs and settings and makes it a tool with no code. asset.make chains tools into a recipe, queues candidates together and has Claude pick the best one against the project's art direction.

AI harnesses

When a harness runs out

  • Studio reads the result for usage, billing, sign-in or transient errors and ignores lines about third parties or its own cloud.
  • The pass is parked with its worktree, session and a handoff note. Parking never counts as a failed try.
  • The harness is held until its stated reset time, and probed every 30 minutes.
  • Other ready harnesses take the parked work. For 6 hours after a usage hold, that harness stays on cheaper tiers.

Known gaps

  • The five non-Claude harnesses ignore the allowed-tools list and run in bypass mode.
  • Skills and subagents are emulated for them as prompt text.
  • They report zero cost, so the ledger prices only Claude passes.
  • Gen's own Claude calls can follow Studio onto Claude, Cursor or Copilot only, and only Claude can read images there.

Where things are stored

  • Studio's database holds every decision and record; it keeps only the ids of Gen's files, never the files.
  • Gen's library bucket is the one home of every generated file, written once by content hash.
  • Work buckets hold run folders, build folders and agent job folders, all disposable.
  • R2 holds beta sites and Unity build files.
  • GitHub holds code, the asset lock files, and the shared memory as Markdown on a branch.

On a crash, each service loses at most about a second of database writes and up to 30 seconds of small settings files. Running jobs resume from their run folders.

GitHub and deploys

  • The hook. Every repo has a small workflow that fires on pushes to beta and main (and build-* tags). It asks GitHub for a signed identity token and posts it to Studio. No secret is stored in the repo.
  • What Studio checks. The token's signature, issuer, audience and repo owner. Then: a beta push republishes the beta site, a build tag starts a Unity build of that commit, a main push records the deploy.
  • Where it points. On GitHub, every repo's hook now posts to your cell. The platform Studio does not forward; it only answers that the project is managed elsewhere.
  • Studio's own credentials. A token from the secret manager for your repos, and a GitHub App with per-repo tokens for customers.
  • Going live. A fast-forward of main with force off. If branch rules block it, Studio opens and merges a pull request. Rollback is a new commit with the old contents, never a force push.
  • Deploying Studio and Gen. A push to beta or main builds the image, updates Cloud Run with no stored key, health-checks it and moves traffic back if it fails. No tests run in that workflow.
  • Worker images. Tags such as gpu-image-* and playtest-image-* build the GPU and playtest images.
  • Local lanes. Each repo has the same six batch files; deploy-beta tags a beta version and deploy-prod asks you to type DEPLOY.

How a project plugs in

  • A project record in Studio: engine, repo, live address, how it builds, its scenarios, its quality bar and its story.
  • Generation through Gen: a preset for its art direction, and optionally an asset manifest whose lock file records what made each file.
  • Agent guidance: an AGENTS.md, content skills, and the Gen and Studio MCP servers.

Where docs lag code

  • The daily loop. Docs describe a daily build, play and review of every product. The code plays only at milestones and go-live.
  • The product registry. Docs call Studio's products.json the registry. It is empty; projects live in the cell's data.
  • Gen's defaults. The code still defaults to the AWS fleet, AWS build box and S3. Only the live settings point at RunPod, Cloud Run and Google storage, so a fresh install would aim at AWS.
  • Pricing. Estimates and customer credit quotes are computed from the AWS GPU price whichever provider runs the job.
  • CI. Docs say CI runs typecheck and tests. The workflows deploy without running them.
  • Unity build help. The debugging skill still describes the AWS Windows build server.
  • Unity packages. Yooba Land and Breaking Through reference Hawkes packages by a path on your PC, which a cloud build cannot see.
  • Leftovers. AWS deploy scripts in Studio, Gen, the portal and Net; a dead Grok adapter; pasted log files tracked in Studio's repo root.

  • Net. Read 41 commits behind, and only at the level of its design doc.
  • GitHub Pages source per repo and the contents of GitHub and Cloudflare secrets.
